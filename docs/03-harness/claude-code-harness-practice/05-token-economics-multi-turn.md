## 1. 上下文窗口的组成结构

以 200K Token 的上下文窗口为例：

```
┌────────────────────────────────────────────────────────┐
│                  200K Token 上下文窗口                   │
├────────────────────────────────────────────────────────┤
│  System Prompt（固定）                                   │
│  ├── Anthropic 内置规则：~3000-8000 Token               │
│  ├── CLAUDE.md：按内容大小                               │
│  └── SKILL.md / Rules：按内容大小                        │
├────────────────────────────────────────────────────────┤
│  对话历史（累积增长）                                     │
│  ├── 历史 Human 消息                                     │
│  ├── 历史 Assistant 消息                                 │
│  └── 工具调用结果（最大的噪声来源！）                      │
├────────────────────────────────────────────────────────┤
│  Tools 定义（固定）                                       │
│  每个工具的 JSON Schema 描述：约 200-500 Token/工具        │
├────────────────────────────────────────────────────────┤
│  Safety Margin（预留给输出）                              │
│  通常预留 8K-16K 给模型输出使用                           │
└────────────────────────────────────────────────────────┘
```

### 关键规律：输出 Token 也会消耗输入空间

LLM 是**自回归**的：每生成一个 Token，它就成为下一个 Token 的"输入"。
从 API 视角看：上轮的 assistant 输出在下轮会出现在 messages 数组里，**作为输入重新传递**。

## 2. 书中第 115 页的多轮对话表格解析

### 2.1 场景设定

```
假设条件：
  System Prompt: 5,000 Token
  既有对话历史: 8,000 Token
  测试输出（噪声）: 10,000 Token
  每轮新增内容:  1,000 Token
```

### 2.2 不用子智能体的累计消耗（每轮都要重传噪声）

| 轮次 | System | 历史 | 噪声（重传） | 当轮合计 | 累计合计 |
|------|--------|------|-------------|---------|---------|
| 第5轮 | 5,000 | 8,000 | 10,000 | 23,000 | 23,000 |
| 第6轮 | 5,000 | 9,000 | 10,000 | 24,000 | 47,000 |
| 第7轮 | 5,000 | 10,000 | 10,000 | 25,000 | 72,000 |
| 第8轮 | 5,000 | 11,000 | 10,000 | 26,000 | 98,000 |
| 第9轮 | 5,000 | 12,000 | 10,000 | 27,000 | 125,000 |

**第5轮到第9轮，5轮累计消耗：125,000 Token**

> ⚠️ **关键问题**：10,000 Token 的测试噪声，每轮都要完整重传一遍。5轮 = 重传 5 次 = 白白浪费 50,000 Token。

### 2.3 使用子智能体后的消耗对比

**子智能体内部（独立上下文，一次性花掉）：**

| 子智能体轮次 | System | 任务描述 | 累积输出 | 合计 |
|-------------|--------|---------|---------|------|
| 第1轮 | 5,000 | 500 | - | 5,500 |
| 第2轮 | 5,000 | 500 | 3,000 | 8,500 |
| 第3轮 | 5,000 | 500 | 6,000 | 11,500 |
| 第4轮 | 5,000 | 500 | 10,000（完整输出） | 15,500 |

**子智能体合计：41,000 Token**（一次性花掉，**不污染主对话**）

**主对话（只收到 100 Token 摘要）：**

| 轮次 | System | 历史 | 摘要（替代噪声） | 当轮合计 | 累计合计 |
|------|--------|------|----------------|---------|---------|
| 第5轮 | 5,000 | 8,000 | 100 | 13,100 | 13,100 |
| 第6轮 | 5,000 | 9,000 | 100 | 14,100 | 27,200 |
| 第7轮 | 5,000 | 10,000 | 100 | 15,100 | 42,300 |
| 第8轮 | 5,000 | 11,000 | 100 | 16,100 | 58,400 |
| 第9轮 | 5,000 | 12,000 | 100 | 17,100 | 75,500 |

**主对话5轮合计：75,500 Token**

### 2.4 总体对比

```
总消耗 = 子智能体 41,000 + 主对话 75,500 = 116,500 Token

节省 = 125,000 - 116,500 = 8,500 Token
节省比例 = 8,500 / 125,000 ≈ 6.8%
```

### 2.5 为什么节省比例会随对话增长而增大？

噪声的累积效应：

```
不用子智能体：10,000 Token 噪声 × 每轮重传
  5轮 = 重传 50,000 Token
  10轮 = 重传 100,000 Token
  20轮 = 重传 200,000 Token  ← 白白浪费 200K！

用子智能体：噪声只在子智能体内部消耗一次 ≈ 15,500 Token
  5轮后节省: 50,000 - 500 = 49,500 Token（对比噪声）
  20轮后节省比例 > 50%（书中数据）
```

**对话轮数越多，子智能体节省的效果越显著。**

## 3. Token 消耗的自回归本质

```
第1轮：
  输入: [System] + [User: "问题"]
  输出: [Assistant: "回答A"]  ← 输出产生

第2轮：
  输入: [System] + [User: "问题"] + [Assistant: "回答A"] + [User: "追问"]
  ↑ 第1轮的输出"回答A"变成了第2轮的输入！
  输出: [Assistant: "回答B"]

第3轮：
  输入: [System] + [User] + [Assistant: A] + [User] + [Assistant: B] + [User: "再问"]
  ↑ 每轮输出都累积成下轮输入，上下文不断膨胀
```

**这是 Context Compaction 存在的根本原因。**

## 4. 三种成本控制策略

### 策略一：子智能体隔离噪声

适用场景：
- 大量文件读取（通常超过 5 个）
- 高频输出（完整测试报告、详细日志）
- 上下文完整性保护（当前任务是复杂工作流的一环）
- 操作权限与安全边界（涉及敏感操作需要沙箱隔离）

### 策略二：Context Compaction

适用场景：单一长任务，需要在不重启的情况下持续工作。
效果：200K 历史压缩为 ~4K 摘要，循环无缝继续。

### 策略三：@ 引用而非内嵌

```markdown
# 低效写法（占用 Token 且不可维护）
遵循以下规则：
[把500行规范文档内容直接粘贴在这里]

# 高效写法（延迟加载）
参考规范：@docs/coding-standards.md

# 区别：
# - @ 引用：Claude 按需读取，不在 CLAUDE.md 里占 Token
# - 直接写：每次对话都加载完整内容
```

### 策略四：Skills 的按需加载

```
CLAUDE.md 常驻加载 ≈ 2000-3000 Token（始终在 System Prompt 里）
SKILL.md  按需加载 ≈ 2000-3000 Token（只在触发时加载）

结论：把不常用的规范放在 SKILL.md 而不是 CLAUDE.md
```

## 5. 500行法则的 Token 经济学根据

书中建议 SKILL.md 控制在 500 行以内，约等于 2000-3000 Token。原因：

```
Claude 200K 上下文窗口分配（实际可用部分）：

System Prompt（固定）:          8K - 15K Token
对话历史（动态增长）:           50K - 100K Token
工具定义（固定）:                3K - 8K Token
Safety Margin（预留输出）:      8K - 16K Token
─────────────────────────────────────────
可供 CLAUDE.md + Skills 的预算: 约 20K - 60K Token
```

若一个 SKILL.md 超过 500 行（>3000 Token），且项目有 5-10 个 Skills，System Prompt 就会被大量知识占满，真正重要的对话历史和工具结果反而空间不足。

**解决方案：500 行法则**
- SKILL.md 主体 ≤ 500 行：操作步骤、核心规则
- 详细规范 → 移至 `reference/` 目录（按需读取，不占 Token）
- 完整示例 → 移至 `examples/` 目录（只在需要时引用）
- 可执行脚本 → 封装到 `scripts/` 目录（工具调用时执行）

## 6. 重构信号表（来自书中表 3-5）

当 SKILL.md 内容超载时，按以下信号重构：

| 重构信号 | 对策 |
|---------|------|
| 大段公式或规范说明 | 移至 `reference/` 目录 |
| 多个完整示例（单个超 30 行） | 移至 `examples/` 目录 |
| 多个输出模板 | 移至 `templates/` 目录 |
| 可独立执行的逻辑 | 封装为 `scripts/` 脚本 |
| 多个平行的功能模块 | 考虑拆分为多个独立 Skill |
